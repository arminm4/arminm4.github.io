Operational databases are built to *run* the business. A **data warehouse** is built to *understand* it. This week you'll learn how to model data for analysis (the star schema), how data gets there (ETL), and the tools that do it: SSIS for ETL, SSAS for analytical models, and Metabase for self-service dashboards. You'll also build a small star schema from the shop database, in SQL, right in the browser.

# Lesson: Why a data warehouse? (20 min)

Running heavy analytics directly on the production database causes problems:

- **Performance**: a 5-minute report query competes with customers placing orders.
- **Integration**: the truth is spread across systems (shop DB, CRM, ads platform, Excel files).
- **History**: operational systems overwrite values (a customer's current city). Analysis needs history (the city *at the time of each order*).
- **Usability**: normalized schemas with 200 tables are hard for analysts to query.

A **data warehouse (DW)** is a separate database that is:
- **Integrated**: data from many sources, cleaned and conformed (one definition of "customer").
- **Historical**: it keeps change history.
- **Subject-oriented and read-optimized**: modeled around business processes (sales, inventory) for fast queries.

### Architecture

```text
Sources            Staging            Warehouse (star schemas)        Consumption
───────            ───────            ────────────────────────        ───────────
Shop DB  ─┐                           ┌─ fact_sales ─┐
CRM      ─┼─► Extract ─► raw copies ─►│  dim_date    │─► semantic model ─► Power BI
Ads API  ─┤   (ETL/ELT)  + cleaning   │  dim_product │   (SSAS / PBI)     Metabase
Excel    ─┘                           └─ dim_customer┘                    Excel, SQL
```

A **data mart** is a subject-specific slice of the warehouse (for example a marketing mart). A **data lake** stores raw files (CSV, JSON, Parquet) cheaply. Modern **lakehouses** (Databricks, Fabric, Snowflake) blur the line between the two.

> [!recap]
> - The warehouse separates analytics from operations: integrated, historical and read-optimized.
> - Flow: sources → staging → warehouse → semantic model → reports.

# Lesson: Dimensional modeling: facts, dimensions, star and snowflake (35 min)

Ralph Kimball's **dimensional modeling** is the standard way to design warehouses.

- A **fact table** records **measurements of a business process event**: one row per order line, payment or website visit. It holds numeric **measures** (quantity, revenue) plus **foreign keys** to the dimensions.
- **Dimension tables** hold the **context** you filter and group by: who (customer), what (product), when (date), where (store), how (channel). They're wide and descriptive.

```text
                 dim_date
                    │
dim_customer ── fact_sales ── dim_product
                    │
               dim_channel
```

This is a **star schema**: one fact table in the centre, with denormalized dimensions around it.

### Step 1: Declare the grain

The **grain** states exactly what one fact row represents: "one row per product per order line". Every measure and dimension must be true at that grain. Getting the grain wrong causes the fan-out double-counting you saw in week 1.

### Step 2: Choose the dimensions and measures

| Measure type | Example | Can you SUM it? |
|---|---|---|
| **Additive** | revenue, quantity | Across all dimensions |
| **Semi-additive** | account balance, inventory level | Not across time (use the last value) |
| **Non-additive** | unit price, margin %, ratios | Never sum: recompute from additive parts |

> [!mistake] Summing percentages
> Store `revenue` and `margin` (additive), and compute margin % = SUM(margin)/SUM(revenue) at query time. Never store and sum a percentage column.

### Surrogate keys and the date dimension

Dimensions get **surrogate keys**: integers generated by the warehouse (`customer_key`), separate from the source system's natural key (`customer_id`). They protect against source changes and enable history tracking (SCD below).

Every warehouse has a **date dimension**: one row per day, with attributes like year, quarter, month name, weekday, is_weekend and fiscal period. It makes time grouping trivial and consistent.

### Star vs snowflake

In a **snowflake schema**, dimensions are normalized: `dim_product → dim_category`. That saves a little space but adds joins. **Prefer star schemas for BI tools.** Power BI, SSAS and Metabase all perform best and are easiest to use with stars.

### Slowly Changing Dimensions (SCD)

What happens when a customer moves from Shiraz to Tehran?

| Type | Strategy | Effect on history |
|---|---|---|
| **SCD 0** | Never change | The original value is kept forever |
| **SCD 1** | Overwrite | History is lost: old sales now appear "in Tehran" |
| **SCD 2** | Add a new row with `valid_from`, `valid_to`, `is_current` and a new surrogate key | Old sales stay linked to the "Shiraz" version |
| **SCD 3** | Add a `previous_city` column | Limited history |

SCD 2 is the classic answer when history matters.

> [!recap]
> - Facts hold measures at a declared grain. Dimensions hold the descriptive context.
> - Additive vs semi-additive vs non-additive measures.
> - Surrogate keys, a date dimension, star over snowflake, and SCD type 2 for history.

# Lesson: Build a star schema in SQL (30 min)

Let's transform the normalized shop database into a small star schema. Run the blocks **in order**. They create new tables in your in-browser database (use **Reset DB** in the Playground to start over).

```sql
-- 1) Date dimension: one row per day for 2024–2025, generated with a recursive CTE
DROP TABLE IF EXISTS dim_date;
CREATE TABLE dim_date AS
WITH RECURSIVE d(day) AS (
  SELECT date('2024-01-01') UNION ALL SELECT date(day, '+1 day') FROM d WHERE day < '2025-12-31'
)
SELECT CAST(strftime('%Y%m%d', day) AS INTEGER) AS date_key, day AS full_date,
       CAST(strftime('%Y', day) AS INTEGER) AS year,
       (CAST(strftime('%m', day) AS INTEGER) + 2) / 3 AS quarter,
       CAST(strftime('%m', day) AS INTEGER) AS month,
       CASE strftime('%w', day) WHEN '0' THEN 'Sun' WHEN '1' THEN 'Mon' WHEN '2' THEN 'Tue'
            WHEN '3' THEN 'Wed' WHEN '4' THEN 'Thu' WHEN '5' THEN 'Fri' ELSE 'Sat' END AS weekday,
       strftime('%w', day) IN ('0', '6') AS is_weekend
FROM d;
SELECT COUNT(*) AS days, MIN(full_date), MAX(full_date) FROM dim_date;
```

```sql
-- 2) Product dimension: denormalize the category into the product (star, not snowflake)
DROP TABLE IF EXISTS dim_product;
CREATE TABLE dim_product AS
SELECT ROW_NUMBER() OVER (ORDER BY p.product_id) AS product_key,
       p.product_id, p.name AS product, c.name AS category, p.unit_price AS list_price
FROM products p JOIN categories c USING (category_id);

-- 3) Customer dimension with a surrogate key
DROP TABLE IF EXISTS dim_customer;
CREATE TABLE dim_customer AS
SELECT ROW_NUMBER() OVER (ORDER BY customer_id) AS customer_key,
       customer_id, name, city, country, COALESCE(segment, 'unknown') AS segment
FROM customers;
SELECT * FROM dim_product LIMIT 3;
```

```sql
-- 4) Fact table at the grain "one row per order line"
DROP TABLE IF EXISTS fact_sales;
CREATE TABLE fact_sales AS
SELECT CAST(strftime('%Y%m%d', o.order_date) AS INTEGER) AS date_key,
       dc.customer_key, dp.product_key,
       o.order_id, o.channel, o.status,
       oi.quantity,
       ROUND(oi.quantity * oi.unit_price * (1 - oi.discount), 2) AS revenue,
       ROUND(oi.quantity * (oi.unit_price * (1 - oi.discount) - p.cost), 2) AS margin
FROM order_items oi
JOIN orders o        ON o.order_id = oi.order_id
JOIN products p      ON p.product_id = oi.product_id
JOIN dim_product dp  ON dp.product_id = oi.product_id
JOIN dim_customer dc ON dc.customer_id = o.customer_id;
SELECT COUNT(*) AS fact_rows FROM fact_sales;
```

```sql
-- 5) A typical star-schema query: filter by dimensions, aggregate facts
SELECT d.year, d.quarter, p.category,
       ROUND(SUM(f.revenue)) AS revenue,
       ROUND(100.0 * SUM(f.margin) / SUM(f.revenue), 1) AS margin_pct
FROM fact_sales f
JOIN dim_date d    ON d.date_key = f.date_key
JOIN dim_product p ON p.product_key = f.product_key
WHERE f.status = 'delivered' AND d.is_weekend = 1
GROUP BY d.year, d.quarter, p.category
ORDER BY d.year, d.quarter, revenue DESC
LIMIT 12;
```

Every analytical question now has the same shape: **join the fact to the dimensions you need, filter, group, aggregate**. That uniformity is why BI tools love stars.

> [!recap]
> - Build the date dimension once. Denormalize the dimensions. Give them surrogate keys.
> - Define the fact grain, then join to dimensions → filter → aggregate.

# Lesson: ETL and the tools: SSIS, SSAS, Metabase (30 min)

### ETL vs ELT

- **ETL (Extract → Transform → Load)**: transform in a separate engine, then load the clean data into the warehouse. This is the classic approach, and SSIS works this way.
- **ELT (Extract → Load → Transform)**: load the raw data first, then transform it *inside* the warehouse with SQL. This is the modern cloud approach, popularized by tools like **dbt**.

Typical transformation steps: deduplicate, standardize formats (dates, currencies, country names), validate, look up surrogate keys, handle late-arriving data and apply SCD logic.

**Incremental loads**: don't reload everything every night. Load only new or changed rows using a **watermark** (`WHERE updated_at > last_loaded_at`) or change data capture (CDC). Make loads **idempotent**, so re-running a failed night's job doesn't duplicate rows. Use `MERGE`/upsert keyed on natural keys.

### SSIS: SQL Server Integration Services

Microsoft's ETL tool, which you build visually in Visual Studio (SSDT):
- **Control flow**: the workflow of tasks (run SQL, loop over files, send email, execute a data flow), connected by precedence constraints (success/failure).
- **Data flow**: the row pipeline. A **source** (OLE DB, flat file, Excel) → **transformations** (Derived Column, Lookup, Conditional Split, Aggregate, Slowly Changing Dimension wizard) → a **destination**.
- Packages are deployed to the SSIS catalog and scheduled with SQL Server Agent.

### SSAS: SQL Server Analysis Services

SSAS builds a **semantic model** on top of the warehouse: business-friendly tables, relationships, **measures** and hierarchies, cached for very fast slicing.
- **Tabular** models use the in-memory **VertiPaq** columnar engine with **DAX** measures. This is the *same engine as Power BI* (weeks 4–5).
- **Multidimensional** (OLAP cubes) use **MDX**. It's older but still found in enterprises.
- Benefits: one governed definition of "Revenue" shared by every report, row-level security and speed.

### Metabase: open-source self-service BI

Metabase connects to databases (PostgreSQL, MySQL, SQL Server and more) and lets non-technical users build questions with a GUI, or write SQL, then pin them to **dashboards** with filters. You can run it locally with Docker:

```bash norun
docker run -d -p 3000:3000 --name metabase metabase/metabase
# open http://localhost:3000 and connect it to a database
```

Good use cases: startups, internal dashboards and quick exploration. Compared with Power BI, it has less advanced modeling (no full DAX) but is very quick to adopt.

> [!connect] Pipelines everywhere
> ETL scheduling, idempotency and incremental loads are the same reliability ideas as cron jobs and backups (DevOps week 3), background jobs (Full-Stack week 10) and document-ingestion pipelines for RAG (Agentic week 2).

> [!recap]
> - ETL transforms before loading, ELT transforms inside the warehouse. Load incrementally and idempotently.
> - SSIS moves data. SSAS Tabular serves governed DAX models. Metabase gives fast self-service dashboards.

## Solution

```sql
DROP TABLE IF EXISTS dim_date;
CREATE TABLE dim_date AS
WITH RECURSIVE d(day) AS (SELECT date('2024-01-01') UNION ALL SELECT date(day, '+1 day') FROM d WHERE day < '2025-12-31')
SELECT CAST(strftime('%Y%m%d', day) AS INTEGER) AS date_key, day AS full_date,
       CAST(strftime('%Y', day) AS INTEGER) AS year
FROM d;
DROP TABLE IF EXISTS dim_customer;
CREATE TABLE dim_customer AS
SELECT ROW_NUMBER() OVER (ORDER BY customer_id) AS customer_key, customer_id,
       COALESCE(segment, 'unknown') AS segment
FROM customers;
DROP TABLE IF EXISTS fact_sales;
CREATE TABLE fact_sales AS
SELECT CAST(strftime('%Y%m%d', o.order_date) AS INTEGER) AS date_key, dc.customer_key,
       o.order_id, o.status,
       ROUND(oi.quantity * oi.unit_price * (1 - oi.discount), 2) AS revenue
FROM order_items oi
JOIN orders o ON o.order_id = oi.order_id
JOIN dim_customer dc ON dc.customer_id = o.customer_id;

SELECT c.segment,
       COUNT(DISTINCT f.customer_key) AS customers,
       ROUND(SUM(f.revenue)) AS revenue,
       ROUND(SUM(f.revenue) / COUNT(DISTINCT f.order_id), 1) AS avg_order_value
FROM fact_sales f
JOIN dim_date d     ON d.date_key = f.date_key
JOIN dim_customer c ON c.customer_key = f.customer_key
WHERE d.year = 2025 AND f.status = 'delivered'
GROUP BY c.segment
ORDER BY revenue DESC;
```

Average order value = total revenue ÷ **distinct orders**. Dividing by fact *rows* (order lines) would be wrong, because it's a different grain.

# Exercise: Design a warehouse (no code)

A food-delivery company wants to analyze **deliveries**: delivery time, distance, fee, tip, rating, restaurant, courier, customer, city zone, time of day, and whether the order was late. Write in your notes:

1. The fact table and its **grain**.
2. The list of dimensions with 4–6 attributes each.
3. Each measure, classified as additive, semi-additive or non-additive.
4. Which dimension needs SCD type 2, and why.
5. An incremental load strategy for the fact table.

## Solution

1. **fact_delivery**: one row per completed (or cancelled) delivery.
2. **dim_date** (date, weekday, holiday flag, month, quarter), **dim_time** (hour, part of day, peak flag), **dim_customer** (segment, signup cohort, city), **dim_restaurant** (name, cuisine, price band, zone, rating band), **dim_courier** (vehicle type, tenure band, employment type), **dim_zone** (city, district, urban/suburban).
3. Additive: fee, tip, distance_km, delivery_minutes, count. Non-additive: rating (average it; store the rating plus a rating count), is_late (store it as 0/1 so that `SUM` gives late deliveries and `AVG` gives the late rate). Semi-additive: none here. An "active couriers" snapshot fact would be semi-additive.
4. **dim_restaurant** (price band or cuisine changes) and **dim_courier** (vehicle type changes) affect historical analysis, so use SCD 2.
5. Load nightly with a watermark on `delivered_at`. Upsert by `delivery_id` (idempotent), and re-process the last 2 days to catch late updates such as ratings that arrive after delivery.
